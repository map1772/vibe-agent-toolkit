# Инструменты разработчика для Agent API

Айхан Кызласов, тестовое по вакансии AI-разработчик / LLM Engineer.

Четыре файла, всё на стандартной библиотеке, зависимостей нет.

- `vibe.py`: клиент, который старается не отправить запрос, если тот спишет деньги зря.
- `vibe_fake.py`: локальный двойник вашего API, чтобы отлаживать агента бесплатно.
- `check_live.py`: сверка документации с живым каталогом. Ключ не нужен, работает уже сейчас.
- `bench.py`: измерения в рублях на ваших ценах.

Проверка:

```
python vibe.py --selftest        # 19 проверок логики запроса, без сети
python vibe_fake.py --selftest   # 7 сквозных проверок: клиент против двойника
python check_live.py             # сверка с боевым каталогом моделей
python bench.py                  # замеры: спасённые рубли, цена промаха, скорость отладки
```

## Что нашлось на вашем живом API прямо сейчас

Ключа у меня пока нет, но тулза `list_capabilities` открыта без авторизации,
поэтому каталог моделей я забрал и сверил с документацией. Результат на
31.07.2026: **10 расхождений**.

Две модели документация описывает, а каталог не отдаёт совсем:

```
video   omnihuman-1-5, volcengine-lipsync
```

Сначала я насчитал шесть и ошибся. `grok-ttv-10/20` и `grok-itv-10/20` в каталоге
есть, просто уровнем ниже: в поле `tiers` внутри `grok-ttv` и `grok-itv`, со
своими ценами в `tier_prices`. Разбор в разделе про тиры ниже.
А вот `omnihuman-1-5` и `volcengine-lipsync` описаны у вас
подробно, с посекундной ценой (32 и 42 рубля за секунду, 10 и 14), с примерами
запросов и ограничениями по размеру файла, но в каталоге отсутствуют совсем.
Разработчик, который читает раздел «Оживить и Озвучить», напишет код на модель,
которой нет.

Ещё восемь моделей есть в каталоге, но не описаны в разборах: `seedream-5-lite`,
`nano-banana-2-1k/2k/4k`, `nano-banana-pro-1k/4k` и упомянутые `grok-itv`, `grok-ttv`.

`check_live.py` находит это за пару секунд и без ключа, так что его можно
поставить в CI: документация разъезжается с каталогом тихо, а ловится дёшево.

Он же печатает ещё две вещи, которые видны только в машиночитаемом каталоге:

**Ключ строгой проверки объявлен у 0 моделей из 47.** Разбор выше, в разделе
про первую дыру.

**Поле `partner_only`.** Каталог прямо сообщает, что программное управление
рекламой (кампании Яндекс.Директа, автопилот ставок, доступы к рекламным

## Измерения

`python bench.py` считает на ценах из вашего живого каталога и на локальном
двойнике, который повторяет боевое поведение: без `strict` лишние поля молча
отбрасываются, а деньги списываются.

**Партия из 25 запросов, шесть из них с типичными ошибками** (поле `image_input`
отправлено видео-модели, опечатка в имени параметра, имя модели взято из
документации):

```
как в примерах документации: списано 482.40 р
через клиент:                списано 372.00 р, шесть запросов отбиты до отправки
СПАСЕНО:                     110.40 р, это 22.9 процента бюджета партии
```

**Цена одного промаха полем по вашему прайсу:**

```
seedance-2         1188.00 р
seedance-2-fast     708.00 р
veo3                570.00 р
kling-3.0-pro       549.00 р
kling-3.0-std       250.00 р
в среднем по восьми видео-моделям: 463.38 р за один промах
```

**Скорость цикла отладки.** Тут две величины разной природы, и я помечаю их
прямо в выводе программы, а не сноской:

```
[измерено]  20 итераций на двойнике: 20.4 с
[измерено]  круговое время до вашего хоста: 740 мс на запрос,
            одна только сеть добавит ~14.8 с на 20 итераций
[из документации, НЕ измерено] image идёт 30-90 с, значит 20 итераций это минимум 600 с
```

Отношение примерно 29 раз, но честно это «измеренное против процитированного».
Живого прогона генерации у меня не было, поэтому боевая сторона взята из вашей
документации, той самой, в которой `check_live.py` нашёл расхождения.
Появится ключ, заменю цитату на замер.

**Что можно оспорить в замере партии, и я скажу это раньше вас.** Доля ошибок
(6 из 25) задана мной, а не снята с живых пользователей. Девятнадцать здоровых
запросов стоят одинаково в обоих режимах и на разницу не влияют, они нужны
только чтобы показать долю. Из шести ошибочных один (несуществующее имя модели)
сервер отклонил бы и сам, там клиент экономит не деньги, а время на понятной
ошибке. Реальные деньги дают пять оставшихся. Возьмёте другую долю ошибок,
получите другой процент, сама механика от этого не меняется.

## Тиры моделей: самое дорогое место, которое я сначала пропустил

У части видео-моделей каталог отдаёт поле `tiers` и цены к ним:

```
grok-itv     price 36
  tiers      grok-itv-10 = 196 р, grok-itv-20 = 316 р
```

То есть `grok-itv-10` это не опечатка и не устаревшее имя, а тир той же модели,
дороже базовой в пять с половиной раз. Моя первая версия отбивала его как
несуществующую модель и советовала взять `grok-itv`. Это тихая подмена тарифа:
человек просил один уровень качества, а получил бы другой, дешевле и хуже,
причём с уверенным сообщением клиента, что он помог.

Сейчас клиент знает тиры: `known_models` их видит, `tier_price` отдаёт цену
именно тира, а запрос с тиром уходит как есть. Проверка 17 в `--selftest`.

Отдельная благодарность: это место мне показали в ревью, а не я нашёл сам.
Оставляю здесь как есть, потому что дефект в инструменте против тихих списаний,
сам делавший тихую подмену, стоит помнить.

## С чего я начал

Прочитал документацию целиком и искал не возможности, а места, где разработчик
теряет деньги или время. Нашёл три, они и определили, что делать.

**Первое.** Ошибка в имени поля не возвращает ошибку, она возвращает счёт.
Вы сами пишете об этом прямым текстом: самая частая ошибка агентов это слать
image_input для видео, в ответ приходит чистый text-to-video, а деньги списываются.
Проблема шире одного поля: у `grok-itv` это `image_urls`, у `omnihuman-1-5`
`image_url` в единственном числе, у `motion-control` `character_image_url`, у
`seedance` `first_frame_url`, у image-моделей `image_input`. Пять разных имён
для одной сущности, и промах между ними стоит денег, а не 422.

`strict: true` эту дыру закрывает, и в документации ему посвящён отдельный
раздел с рабочим примером. Проблема в другом, и это стоит сказать точно.

**Ни одна из 47 моделей живого каталога не объявляет `strict` в своей схеме.**
Проверяется одной командой: `python check_live.py` печатает «объявлен у 0
моделей из 47». Слово `strict` встречается в каталоге шесть раз, и все шесть
в свободном тексте (`getting_started`, `features`, `endpoints`), ни разу как
поле конкретной модели.

Человек читает прозу и узнаёт о защите. Агент читает схему и не узнаёт о ней
никогда. Мой клиент защищён только потому, что я прочитал прозу глазами и
вписал флаг руками, а вся остальная его логика строится по схеме и переживает
обновление каталога. Это и есть разрыв: самая важная защита единственная, до
которой машинным путём не дойти.

**Второе.** Песочницы нет. Отладить обработку 429, возврат денег при сбое
провайдера или собственный приёмник вебхуков можно только на боевом ключе, за
живые рубли. При этом отменить запущенную задачу нельзя: видео считается до
тридцати минут, и всё это время вы уже заплатили.

**Третье.** Результат живёт семь дней, включая `display_url`. Значит скачивание
в своё хранилище это не улучшение, а обязательная часть любой интеграции с
первого дня.

## Что делает клиент

```python
from vibe import Vibe

v = Vibe(token, confirm_above=200)

v.generate("video", "grok-itv",            "кот прыгает", image="https://.../cat.png")
v.generate("video", "motion-control-720p", "танец",       image="https://.../hero.png",
           reference_video_url="https://.../move.mp4")
```

Один и тот же аргумент `image=`, и он попадёт в `image_urls` списком в первом
случае и в `character_image_url` строкой во втором. Куда именно класть, клиент
узнаёт из живого `GET /capabilities`, а если каталог недоступен, берёт таблицу
из вашей документации. Модель, которая входную картинку не читает вовсе (та же
`z-image`), вернёт понятную ошибку до запроса, а не потратит деньги на чистый
text-to-video.

Имя модели проверяется по каталогу до отправки. Если написать `grok-itv-10`
(как в документации), клиент ответит «модели нет в каталоге, возможно вы имели
в виду grok-itv» вместо похода на сервер за 422.

Остальное там же:

- `strict: true` уходит всегда, поэтому опечатка возвращается как 422 и стоит ноль рублей;
- ключ идемпотентности один на все попытки одного вызова, поэтому обрыв сети и
  повтор не оплачиваются дважды (случайный UUID на вызов, а не хеш тела: два
  одинаковых промпта это два разных заказа, а не дубль);
- ретраи идут по вашему `retry_after`, а не по своей догадке, чтобы не загнать
  ключ в `key_cooling_down` на полчаса;
- `confirm_above` спрашивает смету и отказывается запускать дорогую генерацию
  без явного `confirm=True`. Полезно там, где цена посекундная и её видно
  только после загрузки файла;
- `save()` забирает файл, пока ссылка жива.

## Что делает двойник

`vibe_fake.py` поднимает локальный сервер, повторяющий контракт: те же пути, те
же коды ошибок, тот же асинхронный цикл со статусами, вебхуки с подписью
HMAC-SHA256 по сырому телу. Генерирует он заглушки, а не картинки, и это
намеренно: задача повторить поведение API, а не нейросетей.

Сценарии, до которых на боевом ключе не добраться, включаются заголовком:

```
X-Fake: rate_limit    # 429 с retry_after
X-Fake: no_balance    # 402
X-Fake: fail          # генерация падает и деньги возвращаются
X-Fake: slow          # долгий ответ, проверить поллинг и таймауты
```

Двойник специально повторяет и неприятное поведение: без `strict` он списывает
деньги и кладёт в ответ `ignored_params`. Так разработчик видит потерю на
локальном стенде, а не на своём балансе.

Сквозные тесты в `vibe_fake.py --selftest` гоняют настоящий клиент против этого
сервера: успешный путь, отклонение опечатки без списания, картинка в правильном
поле, повтор по ключу идемпотентности, возврат денег при сбое, проверка подписи
вебхука. Один из этих тестов на этапе написания нашёл настоящую ошибку в самом
двойнике, когда сервер отправлял 422 и всё равно продолжал списывать деньги.
Оставляю это как аргумент в пользу того, что тесты тут не для вида.

Готовый код я отдельно прогнал через независимое ревью, и оно нашло ещё три
дефекта, все исправлены:

- `strict: true` можно было снять снаружи обычным аргументом вызова, потому что
  пользовательские поля мержились поверх. Главная защита выключалась незаметно;
- двойник отдавал каталог плоским списком, а живой API отдаёт вложенным
  словарём, поэтому против двойника проверка имени модели молча не работала;
- запись ключа идемпотентности шла вне блокировки, и два одновременных запроса
  с одним ключом могли заплатить дважды. Проверено двадцатью параллельными
  запросами, и этот тест лежит в поставке (vibe_fake.py, проверка 5г).

Первый из них ровно того сорта, о котором вся эта работа: защита есть, выглядит
рабочей, а выключается одним словом в вызове.

Второй заход ревью, уже придирчивого, нашёл ещё шесть, и они серьёзнее:

- обе команды самопроверки падали с `UnicodeEncodeError` на консоли без UTF-8
  (обычный cmd, Git Bash, любой редирект в файл). Тесты при этом проходили, но
  проверяющий увидел бы трейсбек и решил, что работа не запускается;
- обрыв сети уходил наружу сырым исключением мимо ретраев, то есть обещание
  «сетевой сбой не оплачивается дважды» ничем не было обеспечено;
- `retry_after: 0` («повторяй сразу») считался пустым значением, и клиент спал
  секунду по умолчанию;
- `_shape` молча выбрасывал лишние значения, когда в поле на одну картинку
  передавали несколько. Тихая потеря входа с полной оплатой это ровно то, против
  чего написан весь клиент, и мой собственный тест закреплял это как норму;
- ответ 200 с не-JSON телом (страница прокси) ронял клиент необработанным
  исключением вместо понятной ошибки;
- `confirm_above` пропускал дорогую генерацию, если смета вернулась без цены:
  порог просто не с чем было сравнить, и защита тихо отключалась.

Всё исправлено, на каждый пункт есть проверка. Проверок стало 16 и 7 вместо
10 и 6.

## Что я предложил бы платформе

Три вещи, по убыванию пользы. Первые две дешёвые.

**1. Включить `strict` по умолчанию, а мягкий режим сделать опцией.**
Сейчас настройка по умолчанию защищает совместимость, а платит за это кошелёк
клиента. Списание за незамеченную опечатку выглядит для человека как обман
платформы, даже когда виноват его собственный код. Обратная совместимость
решается заголовком версии API или флагом в ключе.

**2. Отдавать в `/capabilities` явную роль поля, а не только имя.**
Одна строка вида `"role": "input_image"` рядом с `image_url` избавляет всех
интеграторов от таблицы соответствий, которую сейчас каждый пишет себе сам, и
которая протухает с каждой новой моделью. Я такую таблицу написал, но её
правильное место у вас, а не в моём коде.

**3. Дать песочницу.** Хотя бы тестовый ключ с нулевой ценой и заглушками
вместо результатов. Мой двойник это обходной путь, он повторяет контракт по
документации и потому неизбежно отстанет от вас после первого же изменения.
Если такой сервер будет вашим, он останется точным, а порог входа для новых
интеграторов упадёт: сегодня, чтобы попробовать, надо сначала пополнить баланс.

Отдельно про отмену задачи: её нет совсем. Для видео на тридцать минут это
заметно, но я понимаю, что упирается в апстрим-провайдеров и дешёвым решением
не будет, поэтому в список выше не ставлю.

## Границы, чтобы не выглядело лучше, чем есть

- Генерации на живом API не проверены: регистрация упирается в капчу, ключа у
  меня пока нет. Проверено на живом контуре другое, и это важная часть: каталог
  моделей забран с боевого MCP и клиент разбирает именно его схему, а не
  выдуманную. Дайте ключ, и я прогоню генерацию, отчёт пришлю с реальными
  ответами и суммами списаний.
- Таблица соответствия полей собрана из документации на 2026-07-30 и нужна
  только как запасной вариант. Основной источник это `/capabilities`, поэтому
  клиент переживает пополнение каталога.
- Я сознательно не трогал MCP-часть, Brand Voice и мост Bitrix24: там у вас
  всё сделано аккуратно, идемпотентность и dry-run на месте, и полезнее было
  закрыть то, где дырка реальная.

## Замер цены промаха именем поля на боевом контуре (02.08.2026)

Раньше цена промаха бралась из прайса. Теперь она снята руками, скриптом `bench_miss.py`, на живом API и с реальным списанием.

**Что сделано.** Модель `grok-itv`, тип `video`, 36 ₽ по каталогу. Картинка положена в поле `image_url` вместо правильного `image_urls`, то есть ровно та опечатка, которую делает агент, знающий соседнюю модель.

**Что вернул боевой `/generate`:**

```json
{"status": "processing", "generation_id": 27190, "cost": 36,
 "balance_after": 62.8, "ignored_params": ["image_url"]}
```

Код 200. Баланс до замера 98,8 ₽, после 62,8 ₽. **Цена одной опечатки: 36 ₽ и результат не тот, что заказывали**, потому что картинка отброшена и видео посчиталось как text-to-video.

Обязательного поля `image_urls` в запросе не было вообще, и это не помешало приёму запроса.

**Защита существует, но живёт не там, где платят.** Тот же запрос, отправленный в `/generate/estimate`, заранее и бесплатно отдаёт всё, чего не хватает:

```json
{"valid": false, "estimated_cost_rub": 36,
 "validation": {"media": [], "required_missing": ["image_urls"]},
 "rejected": ["image_url"]}
```

То есть сервер видит промах до списания, но `/generate` этой проверкой не пользуется. Агент, который не зовёт смету отдельным шагом, платит за каждую опечатку.

**Побочная находка: проверка ссылок отбивает рабочие картинки.** Pre-charge проверка ходит по ссылке методом HEAD. Хосты, которые отвечают на HEAD кодом 405 и при этом нормально отдают файл по GET (например `picsum.photos`), помечаются как `{"ok": false, "code": "unreachable", "http": 405}`, и смета становится `valid: false`. Картинка при этом полностью рабочая. Проверено на двух хостах: `picsum.photos` даёт HEAD 405 и GET 200, `triumph-digital.ru` даёт 200 на оба.

**Что из этого следует для платформы:**

1. Применять к `/generate` ту же проверку, что уже работает в `/generate/estimate`, либо включать `strict` по умолчанию. Сейчас за неверное имя поля платит клиент.
2. Возвращать `ignored_params` до списания, а не вместе с ним.
3. В проверке ссылок падать обратно на GET с диапазоном байт, когда HEAD отвечает 405.
